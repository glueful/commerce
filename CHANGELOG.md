# Changelog

## [Unreleased]

## [1.2.0] - 2026-07-20 — Multi-Vendor Marketplace

The optional multi-vendor marketplace, built as vertical slices MV1–MV5c-2 on top of the single-vendor
core: an opt-in two-level switch, shared partitioned checkout, a commission & settlement ledger,
provider payouts with reserves and chargebacks, seller suspension enforcement, seller API keys, and
isolated per-seller outbound webhooks. Every slice is inert (zero marketplace-table queries,
byte-identical behavior) while the master switch is off. Requires framework 1.71.0 and
extension-contracts 1.5.0; provider payouts and dispute ingestion are fulfilled by payvia 2.1.0
through the neutral contracts ports. Migrations `010`–`019` first-publish together in this release.

**Theme: optional marketplace foundation (MV1)** — a two-level opt-in multi-seller
layer (install master switch + per-workspace activation) with zero behavior change
while off: two new migrations, no changes to any existing table or route.

- Added an optional Marketplace MV1 foundation behind a new install master switch, `commerce.marketplace.enabled` (env `COMMERCE_MARKETPLACE_ENABLED`, default `false`). While off, the marketplace/seller route groups are never registered and ordinary Commerce request paths execute zero marketplace-table queries — existing API behavior stays byte-identical.
- Added per-workspace activation (`commerce_marketplace_settings`) on top of the master switch, guarded by a catalog adoption gate: a workspace cannot activate while any product still lacks a seller, with an optional `default_seller_uuid` to bulk-adopt them. Deactivation is fail-closed and non-destructive — seller/membership/attribution data is untouched, and re-activation re-runs the same gate.
- Added seller identity and lifecycle (`onboarding|active|suspended|closed`) and seller memberships with a fixed, code-defined role vocabulary (`seller_owner|seller_admin|seller_staff|seller_analyst`) behind a `SellerRoleAuthority` seam, plus an anti-lockout last-owner guard on every seller.
- Added catalog ownership: a nullable `commerce_products.seller_uuid`, a dedicated guarded adoption/transfer operation (never a raw patch), and a global per-workspace lock order (workspace → sorted sellers → sorted products) that makes activation-vs-create, close-vs-create, and transfer races deterministic rather than merely test-observed — proven under real two-connection PostgreSQL races.
- Added seller-scoped catalog/inventory/membership APIs (`/commerce/seller/...`) and platform marketplace administration APIs (`/commerce/admin/marketplace/...`), both config-gated behind the master switch and requiring an active workspace for seller-member operational surfaces; operator foundation surfaces (seller/membership CRUD, adoption, transfer) remain available while a workspace is inactive.
- Added migration `010_CreateMarketplaceSellerTables`; the nullable `commerce_products.seller_uuid` column and its `(tenant_uuid, seller_uuid)` index are folded into `001_CreateCommerceCatalogTables` (installs whose catalog migration already ran must add the column/index manually). `DiagnosticsReport` and `commerce:tenancy:adopt` stay marketplace-aware regardless of the master switch, so data created before a switch-off remains coherent.
- No storefront changes: public product payloads never carry `seller_uuid` in MV1.

**Theme: shared checkout & seller orders (MV2)** — one customer order placed at
checkout now fans out into immutable per-seller order partitions with exactly
reconciled money attribution, independent parent-derived fulfillment, and a
payment-confirmation PII gate — inert (zero seller-table queries, byte-identical
behavior) whenever the marketplace workspace isn't active for that order.

- Added shared checkout: a partitioned checkout (marketplace active) computes each seller's exact share of subtotal/discount/shipping/tax/grand-total via a deterministic largest-remainder allocator and writes one immutable `commerce_seller_orders` row per participating seller, alongside the existing single customer order — every reconciliation invariant (`Σ` per-seller = order total, for each of subtotal/discount/shipping/tax/grand-total) is hard-asserted inside the checkout transaction. Value discounts allocate per line; free-shipping allocates the shipping waiver per seller instead. Tax is `line_detailed` when a tax-breakdown is available, else `aggregate_allocated`.
- Added a transfer-safe checkout claim protocol: checkout claims the participating sellers (never the workspace-wide lock) then the participating products, both in ascending UUID order, and re-reads before writing. A concurrent transfer/suspension/closure that changes a product's seller mid-checkout rolls back the whole attempt and retries once automatically from a fresh snapshot; a second drift, or a participating seller that isn't `active`, returns a controlled `409 checkout_conflict` — proven under real two-connection PostgreSQL races (checkout-vs-transfer in both commit orderings, checkout-vs-suspend, checkout-vs-close).
- Added an immutable `commerce_orders.marketplace_partitioned` marker, set once at placement and never mutated: a partitioned order stays child-aware and keeps its `seller_groups` projection forever, even after the workspace later deactivates; a non-partitioned order stays byte-identical regardless of any later activation.
- Added the payment-confirmation seller PII gate: a seller order's `confirmed_at` is stamped on every child, atomically with the parent's `pending_payment → paid` transition, in the SAME database transaction — proven to commit or roll back together under real two-connection contention. A pending or pre-payment-canceled seller order is a non-revealing 404 on every seller-facing surface; a paid-then-canceled order remains seller-visible as history.
- Added independent, parent-derived fulfillment: each seller order carries its own `fulfillment_status`/carrier/tracking; the parent's `fulfillment_status` (`unfulfilled|partial|fulfilled`) rolls up from its children and the parent order transitions to `fulfilled` only once every non-canceled child is. Every fulfillment mutation claims the parent's `fulfillment_revision` before any child, so concurrent child fulfillments serialize and the rollup — and the `OrderFulfilled` event — can never double-fire, proven under real two-connection PostgreSQL races. Whole-order cancellation (from `pending_payment` or `paid`) fans out to every child; partial (single-seller) cancellation is deferred to a future release.
- Added seller-facing order surfaces (`GET /commerce/seller/{sellerUuid}/orders`, `GET .../orders/{sellerOrderUuid}`, `POST .../orders/{sellerOrderUuid}/fulfill`) exposing only that seller's own confirmed lines, allocated totals, and a normalized shipping-only customer address allowlist; operator surfaces (`GET /commerce/admin/orders/{uuid}` breakdown, `POST .../seller-orders/{sellerOrderUuid}/fulfill`, existing fulfill/cancel endpoints) gain full-visibility seller-order detail and fan-out; the consolidated customer order projection (`GET /commerce/orders/{number}`) gains an allowlisted `seller_groups[]` array only when the order is partitioned.
- Added migration `011_CreateSellerOrderTables` for the new `commerce_seller_orders` table; the `commerce_order_lines` (`seller_uuid`, `discount_amount`, `tax_amount`, plus a `(order_uuid, seller_uuid)` index) and `commerce_orders` (`marketplace_partitioned`, `fulfillment_revision`) columns are folded into `004_CreateCommerceOrderTables` (installs whose order migration already ran must add these columns/index manually). `DiagnosticsReport` and `commerce:tenancy:adopt` treat `commerce_seller_orders` as marketplace-aware regardless of the master switch, exactly like the MV1 trio.
- No behavior change while the master switch is off, or for a non-partitioned order once it's on: checkout/payment/fulfillment/cancellation/projection execute zero marketplace-table queries and the customer projection never carries `seller_groups`.

**Theme: commission & settlement ledger (MV3)** — every payment-confirmed and
refund-completed partitioned order posts commission and settlement facts to an
append-only per-account ledger atomically with the lifecycle transition; balances
derive from the ledger; operators run manual payouts and audited commission-policy
changes; sellers and operators get financial reports — inert (zero settlement-table
queries, byte-identical behavior) whenever the marketplace workspace isn't
partitioned for that order.

- Added operator-only commission policy (`percentage` or `fixed`, resolved product → seller → workspace → `config/commerce.php` `marketplace.commission`, which is concrete and never all-null) with a durable, append-only `commerce_commission_policy_events` audit row written in the SAME transaction as every policy mutation — audit-insert failure rolls back the mutation. Sellers may read effective and snapshotted commission policy but never write it; the seller catalog write path rejects any commission field with a field-specific `422` on create and update.
- Added an immutable per-line commission snapshot at checkout (`commission_source/kind/bps/fixed/basis/amount`) plus each seller order's exact summed `commission_amount` — resolved and written once, never rewritten by a later policy edit.
- Added an append-only `commerce_marketplace_ledger` with canonical per-account identity (`seller:{uuid}` | `marketplace`), signed integer-minor-unit amounts, a closed entry-type vocabulary, and deterministic idempotency (a duplicate posting key verifies every immutable field and either no-ops or fails loud — never a duplicate row). A per-`(tenant, account_key, currency)` account lock (`commerce_ledger_account_locks`, the MV1 workspace-lock idiom generalized) serializes every balance-affecting posting, claimed in sorted account-key order across multi-seller postings.
- Added atomic payment posting: `markPaid()` posts each participating seller's `sale_credit`/`commission_debit` inside its own transaction, after payment confirmation and before the `OrderPaid` event — any posting failure rolls back the paid transition itself.
- Added atomic refund posting: `applyCompletion()` derives each refund line's merchandise-capped contribution and per-line cumulative commission reversal at completion time (never at gateway-reservation time, so concurrent refunds against the same line always net out exactly), posts per-seller `refund_debit`/`commission_reversal` plus any unattributable remainder to the marketplace account, and hard-asserts the posted total equals the refund amount exactly.
- Added derived, currency-separated balances (`available`, `reserved`, `paid_out`, lifetime gross sales/commission/refunds/commission-reversed/adjustments) — always a fresh `SUM` over the ledger, never a stored mutable balance.
- Added manual operator payouts (`POST /commerce/admin/marketplace/payouts`): claims the seller account lock, rechecks available balance under it, and refuses (`422`) an amount that would overdraw — proven under real two-connection PostgreSQL races that a concurrent payout can never overdraw a concurrently-refunded account, in both commit orderings. Added operator ledger adjustments (`POST /commerce/admin/marketplace/adjustments`) for signed, reasoned corrections that may drive a balance negative — compensating-entry only, never an edit.
- Added a read-only `commerce:marketplace:reconcile` command that scans paid orders, completed refunds, and payouts directly (never by parent order status) for a missing, duplicated, or mismatched posting — it never posts.
- Added seller (`GET /commerce/seller/{sellerUuid}/financials/...`) and operator (`GET /commerce/admin/marketplace/financials/...`, `.../sellers/{uuid}/balance`, `.../sellers/{uuid}/report`) financial report/balance/payout/commission-policy surfaces, all config-gated behind the master switch.
- Added migrations `012_CreateMarketplaceLedgerTables` (ledger, account locks, commission-policy events) and `013_CreatePayoutTable`; commission columns are folded into `001_CreateCommerceCatalogTables` (products), `004_CreateCommerceOrderTables` (order lines), and `010_CreateMarketplaceSellerTables` (sellers, workspace settings), and the seller-order commission sum into `011_CreateSellerOrderTables` (installs whose migrations already ran must add these columns/tables manually). `DiagnosticsReport` and `commerce:tenancy:adopt` treat all four new tables as marketplace-aware regardless of the master switch, exactly like the MV1/MV2 tables.
- No behavior change while the master switch is off, or for a non-partitioned order once it's on: checkout/payment/refund/fulfillment execute zero settlement-table queries and post nothing.

**Theme: provider payouts (MV4)** — a provider-neutral payout/transfer saga on top
of the MV3 settlement ledger: real money moves to a seller through a configured
payments provider, with in-flight balance protection, bounded automatic retries,
provider reconciliation, and provider-reported reversals — inert (manual payouts and
all ledger semantics unchanged, zero new queries) whenever no provider is bound.
Release chain: `glueful/extension-contracts` 1.5.0 → `glueful/payvia` 2.1.0 →
`glueful/commerce` 1.2.0; commerce depends on the contract only, never on payvia.

- Added the reserve → execute → finalize payout saga (`PayoutService::execute()`, mirroring `RefundService`'s gateway saga): reserve claims the seller account lock, rechecks available balance under it, refuses (`422`) before any hold if the destination isn't provider-`ready` or the amount would overdraw, then posts a `reserve_hold` and commits — all before any provider I/O. Execute calls the bound `PayoutCollector::transfer()` strictly outside any database transaction. Finalize claims the payout out of `pending` via a single-finalizer-wins CAS and applies the outcome: `PAID` converts the hold into a real debit; `PENDING`/`UNKNOWN` leave the hold standing and schedule a reconcile; a confirmed `RETRYABLE_FAILURE` keeps the hold and schedules the next attempt (or terminalizes and releases the hold on the final allowed attempt); `TERMINAL_FAILURE` releases the hold immediately. An `UNKNOWN` outcome (or a transport throw) never advances the attempt and always raises `PayoutOutcomeUnknownException` — only a reconcile may resolve it.
- Added a `pending` seller-balance component, split from `reserved` by whether a ledger hold references a payout: an in-flight provider payout now shows as `pending` while a hold from any other future use (e.g. a risk reserve) would show as `reserved` — the two never collide. `available`/`paid_out` semantics are unchanged.
- Added per-attempt provider idempotency: attempt `n` uses the deterministic key `{payoutUuid}:attempt:{n}` for both its `transfer()` call and every `status()`/reconcile call about that same attempt; a new attempt key is minted only after a *confirmed* retryable failure, never while an attempt is `UNKNOWN`/`PENDING`.
- Added bounded automatic retries: `PayoutRepository::claimRetryableForAttempt()` is a guarded CAS from `failed+retryable+due` to `pending` that increments `attempt_count`, clears the backoff timer, and re-arms a reconcile watchdog *before* any provider I/O runs, so a crash right after a claim is recovered by reconciliation rather than a blind second retry. The operator single-payout retry (`POST /commerce/admin/marketplace/payouts/{uuid}/retry`) uses the identical CAS but may bypass the due-time wait; neither path can exceed the configured `max_attempts`, and a terminal/exhausted payout is never resurrected.
- Added provider reconciliation (`PayoutService::reconcile()`, contract-only — commerce never reads payvia's own tables): resolves a still-unresolved `pending` attempt via `PayoutCollector::status()`, and — on a slower cadence — scans `paid` payouts for provider-reported reversals. A cumulative `reversedAmount` posts only the unseen delta as a `payout_reversal` (partial reversals stay `paid`; a full reversal reaches `status=reversed`); a provider regression on an already-paid row (an unexpected status, or a `reversedAmount` that goes backward or exceeds the payout) is logged as an integrity finding and never reposts or releases money. There is no operator "reverse"/clawback endpoint — MV4 only processes what the provider itself reports.
- Added provider-sourced payout-destination readiness: a new `commerce_seller_payout_accounts` table (one opaque, provider-owned `account_ref` per tenant/seller/provider) whose `readiness_state` is set only by syncing from `PayoutCollector::inspectDestination()` — never by an operator "mark ready". Reserve refuses (`422`) unless a `ready` account exists for the payout's provider, checked before any lock claim or hold. Inspection I/O never runs under a database lock; a concurrent account replacement makes a stale inspection result a no-op instead of marking the wrong destination ready, and an in-flight payout keeps its snapshotted destination even if the account is later reattached.
- Added scheduled payout batches (`commerce:marketplace:payouts:run-batch`, CLI-only — no HTTP batch action) and sweeps (`:payouts:retry-sweep`, `:payouts:reconcile-sweep`, `:payouts:sync-payout-accounts`): the batch amount is derived from the seller/currency account's *locked* available balance at the moment the account lock is claimed (never an unlocked candidate hint), optionally capped by a per-currency maximum and skipped below a per-currency minimum — this is what lets concurrent batch workers serialize on the account lock instead of ever duplicating an amount. Every sweep processes candidates independently, so one seller's failure never aborts the rest.
- Added operator (`POST .../payouts/execute`, `POST .../payouts/{uuid}/retry`, `POST`/`POST .../payouts/accounts[/sync]`, all `commerce:write`) and seller (`GET .../payouts/accounts`, provider/state/last-synced only, never the opaque `account_ref`) HTTP surfaces, config-gated the same way as every other marketplace route; the existing seller payouts list gains sanitized status/provider/provider_ref/failure fields while the pre-MV4 manual-payout projection stays byte-identical. `PayoutException` maps to a clean `422`, never a `500`.
- Folded the provider-payout columns (`status`, `method`, `provider`, `provider_ref`, `destination_ref`, `failure_code`/`reason`, `retryable`, `attempt_count`, attempt/reconcile timing, `reversed_total`, `completed_at`) directly into the still-unreleased `013_CreatePayoutTable` migration alongside two new retry/reconcile sweep indexes, and added migration `014_CreateSellerPayoutAccountsTable`; `external_ref`/`created_by` become nullable at the schema level (a provider row is written before either is known) while the manual `record()` service continues to require both explicitly. `DiagnosticsReport` and `commerce:tenancy:adopt` treat `commerce_seller_payout_accounts` as marketplace-aware regardless of the master switch, exactly like every other settlement table.
- No behavior change with the master switch off or with no `PayoutCollector` bound: manual payouts and all ledger semantics are unchanged byte-for-byte, the provider saga is cleanly unreachable (a `422`, never a fatal error), zero new queries touch the payout-destination table or its sweep indexes on ordinary request paths, and an old-shaped payout insert that never knew these columns existed still reads back `status=paid, method=manual`.

**Theme: risk, reserves & negative balances (MV5a)** — rolling per-seller reserves,
provider-reported chargebacks, and negative-balance/debt recovery on top of the MV3/MV4
settlement ledger — inert (zero reserve holds, zero chargeback rows, byte-identical
manual/refund/payout behavior) whenever no reserve policy is configured and no
chargeback is ingested. Ships in the SAME bundled release train as MV4: `glueful/framework`
1.71.0 → `glueful/extension-contracts` 1.5.0 → `glueful/payvia` 2.1.0 → `glueful/commerce`
1.2.0; migrations `010`–`016` first publish together in that release. Commerce depends on
the contract event only, never on payvia.

- Added rolling per-seller reserves: a two-level `reserve_bps`/`reserve_days` policy (per-seller override, nullable, falling back to a workspace default; `0` on either level disables the reserve for that level without inheriting) resolves once at settlement and is snapshotted onto each hold — a later policy change never touches an existing hold. The reserve base is the seller's net merchandise proceeds after commission, excluding tax and shipping (`max(0, subtotal - allocated_discount - commission_amount)`, cross-checked against the equivalent `attributed_total - allocated_shipping - allocated_tax - commission_amount`), floored at zero; `release_at` is the seller order's own `confirmed_at` plus the snapshotted `reserve_days`. Every workspace/per-seller policy mutation writes an append-only `commerce_reserve_policy_events` audit row in the same transaction as the change.
- Added a scheduled, idempotent reserve-release sweep (`commerce:marketplace:reserves:release-sweep`, host-cron-invoked CLI, no in-process scheduler) that claims each due hold's seller/currency account lock, re-derives its remaining amount fresh from the ledger, and releases only the positive remainder — a hold already partially consumed by an earlier chargeback or refund releases exactly what's left, never a stale original amount, and never twice.
- Added durable, idempotent provider chargeback ingestion via a new inbound `ProviderChargebackEvent` contract (event-first: the row is inserted before any posting, under a `(tenant, provider, provider_event_id)` idempotency claim that verifies an exact-payload replay and rejects a conflicting reuse as an integrity error). A full chargeback (equal to the original charge) auto-expands proportionally across seller-order lines via a deterministic largest-remainder allocator and posts atomically in the same transaction; a partial chargeback requires an operator to supply explicit line attribution before it posts. Attribution keys off the immutable per-line seller snapshots, never live seller data. Eligibility follows the order's own immutable `marketplace_partitioned` marker, never current workspace activation — a historical partitioned order keeps ingesting chargebacks after the workspace later deactivates.
- Added reserve-first, proportional chargeback reversal shared with refunds via one `ReserveConsumptionService`: a seller's net liability draws down held reserves earliest-`release_at`-first (FIFO; indefinite manual holds sort last) before the remaining debit posts in full — the seller debit reverses the full attributed amount including attributable shipping/tax, while the commission reversal stays capped to the merchandise basis using the existing refund-style cumulative cap. A reserve is never over-released (`reserved >= 0` always); any chargeback amount that resolves to no seller line, or exceeds total seller allocations, posts against the marketplace account explicitly, never silently assigned to a seller.
- Added negative-balance/debt: once eligible reserves are exhausted, the remaining chargeback (or refund) debit posts in full, allowing a seller's derived `available` to go negative — there is no separate mutable "debt balance", `debt = max(0, -available)` is purely derived and surfaced alongside `available`/`pending`/`reserved`/`paid_out`. A future `sale_credit` nets debt down automatically through ordinary ledger arithmetic; an in-flight provider payout is never implicitly cancelled by a chargeback arriving mid-payout. Provider and manual payouts now additionally require zero outstanding debt (`debt == 0`), and scheduled payout batches skip any indebted seller — independently, per candidate.
- Added compensating chargeback reversals (a provider-reported dispute win or re-credit) as a SEPARATE event in the same `commerce_chargebacks` table (`kind=reversal`, correlated via `related_chargeback_uuid`) — never a mutation or deletion of the original chargeback's rows. Posts a `chargeback_credit` plus the matching `commission_debit` re-application, capped so cumulative compensation across however many reversal events never exceeds the original's own postings (an over-amount or regressing observation is an integrity finding, never a fabricated positive post); if the original consumed a still-unexpired rolling reserve, the compensation re-holds that same reserve up to what was originally consumed by it, capped at the reserve's own original amount.
- Added audited manual operator overrides layered on top of the rolling-reserve lifecycle: an emergency reserve hold/release (caller-idempotent, actor + reason required, an indefinite hold that never auto-releases) via the same `reserve_hold`/`reserve_release` ledger machinery every other path uses, and an explicit, audited positive `adjustment` for operator debt forgiveness — the chargeback/ledger history stays immutable; forgiveness is a new compensating credit, never a mutation.
- Added a dedicated operator surface (`AdminReserveController`, `commerce:write`/`commerce:read`, 8 routes: workspace/per-seller reserve-policy PATCH, chargeback ingestion + attribution POST, manual reserve hold/release POST, debt-forgiveness POST, and a seller-reserves-plus-debt GET) and a sanitized seller-facing read (`GET .../financials/reserves`: `reserved` total, `debt`, and upcoming reserve releases — amount + `release_at` only, no provider event internals or payment references leaked). No operator "reverse a chargeback" endpoint exists anywhere — reversals are provider-reported only.
- Folded the rolling-reserve policy columns (`reserve_bps`/`reserve_days`, workspace default NOT NULL default `0`, per-seller override nullable) directly into the still-unreleased `010_CreateMarketplaceSellerTables`, and the `reserve_uuid`/`chargeback_uuid` ledger correlation columns (plus indexes) into the still-unreleased `012_CreateMarketplaceLedgerTables` — `LedgerRepository`'s insert/replay-verify allowlist expands from 12 to 14 immutable fields accordingly. Added migrations `015_CreateSellerReservesTable` (durable reserve holds + append-only `commerce_reserve_policy_events` policy audit) and `016_CreateChargebacksTable` (durable `commerce_chargebacks` provider events + `commerce_chargeback_lines` attribution rows); migrations `010`–`016` first publish together in Commerce 1.2.0 — no upgrade migration, no ALTER. `DiagnosticsReport` and `commerce:tenancy:adopt` treat all four new tables as marketplace-aware regardless of the master switch, exactly like every other settlement table.
- Contract-only coupling: Commerce depends only on the neutral `ProviderChargebackEvent` VO (extension-contracts 1.5.0); it never names or reads a payvia table and carries no composer dependency on payvia. The dispatching listener uses the framework's new strict-dispatch seam (`EventService::dispatchOrFail()`, framework 1.71.0) so a failing Commerce listener leaves the durable provider event redispatchable rather than silently swallowed.
- No behavior change while the master switch is off, or with reserve policy `0`/`0` and no chargeback ever ingested: zero reserve holds, zero chargeback rows, no new routes exposed, manual/refund/payout responses stay byte-identical, and an ordinary (non-payout/non-chargeback/non-reserve) request path executes zero queries against any of the four new tables — proven under real two-connection PostgreSQL races that a chargeback's reserve consumption + debit under the shared seller/currency lock can never be overdrawn by a concurrent payout, and that a concurrent reserve-release sweep can never double-release a reserve a chargeback is concurrently consuming.

**Theme: seller suspension & lifecycle enforcement (MV5b)** — makes seller suspension
actually mean something across storefront, checkout, and payouts: soft-delisted from the
storefront and unbuyable at checkout, payouts frozen while the ledger keeps accruing, but
already-placed paid orders stay honored and fulfillable — an operator-only, audited,
prospective, fully-reversible transition. Ships in the SAME bundled release train as
MV4/MV5a: `glueful/framework` 1.71.0 → `glueful/extension-contracts` 1.5.0 →
`glueful/payvia` 2.1.0 → `glueful/commerce` 1.2.0; migrations `010`–`017` first publish
together in that release. Commerce-only — no new framework/contracts/payvia coupling.

- Added mandatory reason + actor on every seller-lifecycle transition (`suspend`/`reactivate`/`close`, `commerce:write`): a blank reason or missing actor is a `422` before any claim or write, and every transition writes an append-only `commerce_seller_lifecycle_events` audit row (`from_status`, `to_status`, `actor_uuid`, `reason`) in the SAME transaction as the `commerce_sellers.status` write — a failed audit insert rolls back the transition too. Re-suspending an already-`suspended` seller (or reactivating an already-`active` one) is a stable no-op that writes no new event; an incompatible transition (reactivating or suspending a terminally `closed` seller, or `onboarding → suspended`) is a controlled `409`, never a `500`.
- Added a centralized buyer-availability predicate (`seller_uuid IS NULL OR seller.status = 'active'`) applied to dedicated buyer reads (`ProductRepository::findBuyerAvailableByUuid/BySlug`, storefront listing/search) and cart add/update/pricing: a suspended or closed seller's products soft-delist from the storefront and are rejected at cart-add with the same stable unavailable-product error a delisted product returns — without ever mutating the product row. Reinstatement restores visibility automatically, with no product-row rewrite. The predicate is a genuine no-op for a sellerless (non-marketplace-store) product and for a product owned by an `active` seller; the shared `findLiveByUuid`/`findLiveBySlug` reads stay tombstone-only and unfiltered for every admin/catalog-mutation/importer/relationship/inventory/media/download/attribution path.
- Added checkout revalidation under the existing MV2 `workspace → seller → product` claim order: a suspended seller fails checkout even for an item added to the cart before suspension, and a checkout can never create an order for a seller after suspension has committed — proven under real two-connection PostgreSQL races in both commit orderings.
- Added payout freeze: `PayoutService` now requires `SellerRepository` and claims the seller's own revision — the SAME primitive `suspend()`/`reactivate()` claims — strictly before the seller/currency ledger account lock, inside both `record()`'s and `reserve()`'s transaction. A new manual or provider payout for a non-`active` seller is refused (a stable `422`) before any lock is claimed or anything posted; a scheduled batch candidate is silently skipped instead. An already-committed manual payout keeps replaying successfully after a later suspension, and an already-reserved provider payout keeps reconciling to completion — suspension never cancels, reverses, or strands in-flight money. The ledger keeps posting normally regardless of status (sale credits, refunds, chargebacks, commissions, reserves/releases, adjustments) — no funds are ever mutated merely because status changed. Proven under real two-connection PostgreSQL races, both commit orderings: a payout is never created for a seller after suspension commits.
- Added a restricted seller-member fulfillment surface while suspended: `commerce_seller:<capability>` gains a route-level `allow_suspended` opt-in, fail-closed by default (a stable `409` on every other seller route) — order list/detail, fulfillment/tracking, balance/financial summary, and reserve history remain available; catalog, inventory, membership, payout, and policy routes do not. The capability check still applies on every opted-in route; `allow_suspended` never grants a capability. Already-placed paid orders remain visible and fulfillable through suspension regardless of the seller's current status, and operator fulfillment is always fully available.
- Added an operator-only, tenant-bound, paginated lifecycle-history read (`GET /commerce/admin/marketplace/sellers/{uuid}/lifecycle`, `commerce:read`, ordered `created_at DESC, id DESC`) with a non-revealing 404 identical for an unknown or cross-tenant seller.
- `close` now also requires a reason and folds into the same lifecycle audit; residual-balance disposition on close remains out of scope for this release — a closed seller's derived balance stays visible and untouched. `closed` shares buyer-unavailability with `suspended` (both excluded by the same predicate) but stays terminal and irreversible — the two states are never otherwise collapsed.
- Added migration `017_CreateSellerLifecycleEventsTable` (`actor_uuid` `NOT NULL` at the schema level); migrations `010`–`017` first publish together in Commerce 1.2.0. `DiagnosticsReport` and `commerce:tenancy:adopt` treat the new table as marketplace-aware regardless of the master switch, exactly like every other settlement table, and the operator lifecycle-history read is paginated and tenant-bound.

A safety-check failure is a terminal delivery failure whose seller-facing message never exposes a resolved internal address.
- Added lease-recoverable, exact-byte signed delivery: each attempt signs the EXACT stored event-snapshot bytes (never a re-encode) with the endpoint's current secret via the framework's `WebhookSignature`, through a crash-safe claim lease (`delivering` status, a random token, and an expiry set before any HTTP I/O runs) — the commit of that claim is the in-flight linearization point. - Added reasoned seller-suspend and endpoint-disable pause (mirroring MV5b's freeze precedent): a delivery generated while its seller is suspended is still durably captured but born `paused` with zero consumed attempts, its remaining retry delay persisted and reconstructed with database time on reinstatement — an endpoint-level pause is entirely independent and never resumed by a seller reinstatement or vice versa. - Added a retention purge command (`commerce:marketplace:webhooks:purge`, host-cron-invoked): deletes `delivered`/`dead_letter`/`canceled` deliveries and their now-orphaned event snapshots older than `commerce.marketplace.webhooks.retention_days` (default 90), scoped per tenant. `pending`, `paused`, and `delivering` rows are never purged — including a `delivering` row whose crash-safe claim lease has already expired, which only the recovery sweep may touch — and a tombstoned endpoint plus its audit trail follow their own, longer, untouched retention policy.
- Added migration `019_CreateSellerWebhookTables` (endpoints, secrets, event snapshots, deliveries, endpoint audit); `DiagnosticsReport` and `commerce:tenancy:adopt` treat all five new tables as marketplace-aware regardless of the master switch, exactly like every other settlement table.

## [1.1.0] - 2026-07-16 — Concurrency Hardening

**Theme: transactional-core hardening** — atomic checkout claims, checked order

422s where concurrent or duplicate input previously produced database errors.
No new env vars, no migrations; error semantics tighten (409/422 where blind
writes or 500s occurred before).

- Hardened the transactional core against concurrent mutation: checkout claims the cart with an atomic active→converted flip (a losing duplicate checkout gets a controlled 422, and a failed checkout restores the cart); cart line/discount/merge mutations serialize through the same claim (merge orders cart claims by UUID to avoid deadlock); every order status transition (payment, cancellation, expiry, fulfillment, full refund) is an affected-row-checked `WHERE status = ?` update, so lifecycle events like `OrderPaid` can no longer double-fire.

- Fixed `POST /commerce/admin/orders/{uuid}/fulfill` returning a 500 for an unknown or
  cross-tenant order; it now 404s exactly like `cancel()`.

  path repository).
