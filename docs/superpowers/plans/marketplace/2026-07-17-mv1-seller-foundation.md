# Marketplace MV1 — Optional Mode & Seller Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship MV1 per `docs/superpowers/specs/marketplace/2026-07-17-mv1-seller-foundation-design.md` (revision 2): the two-level marketplace switch, sellers + memberships behind a role-authority seam, catalog ownership with guarded adoption/transfer, seller-scoped surfaces — byte-identical to today while the master switch is off.

**Architecture:** `MarketplaceMode` (config gate + per-tenant activation) and `MarketplaceWorkspaceLock` (idempotent settings-row ensure + revision claim, the shared serialization boundary) sit under everything; the global mutation lock order (workspace → sorted sellers → sorted products) makes activation-vs-create, close-vs-create, transfer-vs-close/transfer, and owner-demotion races deterministic; seller attribution policy lives in `CatalogService` (not controllers) so no caller can bypass it; seller routes compose `auth → tenant → commerce_seller`.

**Tech Stack:** commerce only; SQLite harness + committed pgsql-gated lane; house claim/DTO/controller/route patterns; REAL migrations (published extension — no folds).

## Global Constraints

- Repo: commerce only, branch dev, commits at group boundaries, no attribution/trailers, never stage docs/superpowers/** or .superpowers/**.
- PUBLISHED-EXTENSION POSTURE: two NEW migrations (`010_CreateMarketplaceSellerTables`, `011_AddSellerToProducts`), never edits to shipped ones; CHANGELOG `[Unreleased]` covers the slice (next release is a minor).
- MASTER SWITCH: `commerce.marketplace.enabled` (env `COMMERCE_MARKETPLACE_ENABLED`, default false). OFF ⇒ marketplace route groups NOT registered, services inert, ordinary request paths execute ZERO marketplace-table queries, existing API behavior byte-identical. EXPLICIT EXCEPTIONS that stay marketplace-aware regardless of the switch: migrations, `DiagnosticsReport` inventories, and `commerce:tenancy:adopt` rekeying (data created before a switch-off must stay coherent).
- PER-WORKSPACE ACTIVATION: `commerce_marketplace_settings` row (`status active|disabled`); single-store activates the sentinel `''`. Seller-MEMBER surfaces require ACTIVE mode (409 otherwise); OPERATOR foundation surfaces (seller/membership CRUD, adoption, transfer) work while inactive — configuration precedes activation, which is what makes first activation possible.
- MASTER-OFF FAST PATH: `MarketplaceMode::installEnabled()` is checked before any workspace claim or marketplace query. OFF executes the existing product-create path byte-identically. Only when the master switch is ON does product creation enter the marketplace transaction/lock protocol.
- GLOBAL MUTATION LOCK ORDER (verbatim, no flow may invert it): workspace-settings claim FIRST; then all participating seller revision claims sorted by seller UUID; then product `catalog_revision` claims sorted by product UUID. Activation = workspace + optional default seller (validated AFTER its claim) + products. Seller-attributed create = workspace + target seller before insert. Close = seller before counting products. Membership mutations = seller before owner-count/write. Adoption/transfer = workspace + optional source/target sellers + product. Transfer snapshots the source before choosing the seller claim set, claims the product, then re-reads it; source drift aborts the transaction with stale-ownership 409 — it NEVER acquires a newly discovered seller after the product claim.
- ACTIVATION GATE (adoption): cannot activate while any non-deleted product lacks a seller; optional `default_seller_uuid` bulk-adopts unassigned products inside the activation transaction (per-product catalog_revision claims); otherwise 409 with the unassigned count. Re-activation re-runs the gate. With the master switch ON, activation/re-activation and EVERY product-create path acquire the workspace lock INSIDE the same transaction as the product insert and BEFORE reading mode or catalog state.
- DEACTIVATION: non-destructive; seller-member surfaces 409; operator foundation surfaces stay; ordinary commerce untouched; re-activation restores.
- SELLER LIFECYCLE: statuses `onboarding|active|suspended|closed`; v1 transitions create→active, suspend⇄reactivate, close. Create REQUIRES `owner_user_uuid` and writes seller + first ACTIVE `seller_owner` membership atomically (an ownerless seller is never externally visible). Close: blocked while the seller owns any non-deleted product; once clear, atomically marks `closed` AND deactivates all memberships — closure is the ONLY transition allowed to retire the final owner ("zero active memberships" is NOT a close precondition). Last-owner invariant applies while `onboarding|active|suspended`. Suspended ⇒ all seller-member MUTATIONS fail closed, reads stay; products remain purchasable (MV1 has no checkout consequences — documented). Slug immutable after create.
- ROLES: `SellerRoleAuthority` seam + shipped `FixedSellerRoleAuthority`; vocabulary EXACTLY `seller_owner|seller_admin|seller_staff|seller_analyst`; v1 capability matrix EXACTLY as spec §2.6 (catalog.read all / catalog.write owner+admin / inventory.read all / inventory.write owner+admin+staff / members.manage owner only). No custom roles/overrides.
- SELLER USERS: authenticated principal (post-auth `user` attribute) + ACTIVE membership row; commerce never queries host workspace membership; middleware order `auth → tenant → commerce_seller` when tenancy enabled, `auth → commerce_seller` in sentinel mode. `commerce_seller:<capability>` resolves the seller from the ROUTE RESOURCE (never a body field), fail-closed.
- ERROR SEMANTICS (verbatim table): master off → routes absent; workspace not activated → seller-member routes 409, operator foundation routes available; unknown seller / no membership / cross-seller / inactive membership → non-revealing 404; suspended/closed seller-member mutation → 409.
- CATALOG OWNERSHIP: `products.seller_uuid` nullable; ordinary create/update DTOs NEVER accept it; seller-scoped create derives it from authorization; plain `POST /products` in an ACTIVE workspace 422s; the attribution policy lives in `CatalogService` (importer/CLI/internal callers cannot bypass); adoption/transfer = one dedicated guarded operator operation (global lock order, post-lock target + source validation, audit event). Children (variants/stock/downloads/media/add-ons/taxonomy) inherit seller strictly via the product root.
- STOREFRONT: zero MV1 exposure — a test pins `seller_uuid` absent from every public payload.
- Every new route annotated (`#[ApiOperation]` + `#[ApiResponse]`); `HttpDocumentationTest` must execute its walk WITH the master flag on so config-gated routes stay enforced. Provider registrations with `use` imports. Tenant scoping on every query; audit-style events on every lifecycle transition; UtcNowSql for raw-SQL timestamps.
- Quality gates per group: `composer test`, `composer phpcs`, `composer run analyze`.

**Files:** create `migrations/010_CreateMarketplaceSellerTables.php` (three tables EXACTLY per spec §3 incl. settings `revision`, memberships indexes `(tenant_uuid,user_uuid)` + `(seller_uuid,status,role)`), `migrations/011_AddSellerToProducts.php` (nullable `seller_uuid` + index `(tenant_uuid,seller_uuid)`); create `src/Marketplace/MarketplaceMode.php`, `src/Marketplace/MarketplaceWorkspaceLock.php`; modify `src/Support/DiagnosticsReport.php` (+3 commerceTables; settings/sellers/memberships → tenantTables), `config/commerce.php` (+`marketplace.enabled`), provider registrations; create `tests/Integration/Migrations/MarketplaceShapeTest.php`, `tests/Integration/Marketplace/MarketplaceModeTest.php`.

**Interfaces (later tasks consume exactly):**
- `MarketplaceMode::installEnabled(ApplicationContext $c): bool` (config only, no DB); `activeFor(ApplicationContext $c, string $tenant): bool` (settings row; NEVER called when installEnabled false).
- `MarketplaceWorkspaceLock::claim(ApplicationContext $c, string $tenant): void` — runs INSIDE the caller's transaction: idempotently ensure a `disabled` settings row exists, then affected-row-checked revision claim. The insert attempt runs in a nested transaction/savepoint; on the verified tenant-unique conflict, roll back that savepoint BEFORE re-reading and retrying the claim, so PostgreSQL's aborted-statement state never poisons the caller's outer transaction. An unrelated insert failure is rethrown.
