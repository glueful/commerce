# Marketplace MV5c-2 — Seller Outbound Webhooks (design)

**Status:** held / uncommitted draft for user hardening.
**Slice of:** the marketplace overview (§MV5 "seller-specific API keys/webhooks"). MV5c-2 is the SECOND, independent MV5c subsystem — **outbound event delivery** — with no coupling to MV5c-1 (API keys). This is the final marketplace slice.

**Scope:** commerce owns the seller-scoped webhook subsystem (endpoints, event snapshots, deliveries, retries, dead-letters, replay, auto-disable, revision locking, suspension/closure). It REUSES framework security primitives only. Bundles into the still-unpublished **Commerce 1.2.0**; new migration(s) `019+`. Release chain **framework 1.71.0 → commerce 1.2.0** (one small framework seam, §4). No contracts/payvia.

**Builds on / reuses (framework, NOT re-implemented):**
- `Glueful\Api\Webhooks\WebhookSignature::generate(payload, secret, timestamp)` — Stripe-style HMAC-SHA256 header `t=…,v1=…` (+ `verify`). Used verbatim to sign the exact stored payload bytes.
- `Glueful\Encryption\EncryptionService` — AES-256-GCM encrypted-at-rest secret storage with key identifiers/previous-key support. Commerce binds each ciphertext to its tenant + endpoint + secret UUID via AAD and returns plaintext only once at creation/rotation.
- The framework's **SSRF-safe outbound validation** — today the private `Client::assertSafeFetchUrl()` behind `Client::safeRequest()`/`safeRequestAsync()` (DNS resolve → reject blocked space → IP-pin the connection while preserving hostname/SNI → no redirects) + the locked `HttpClientConfig::forWebhooks()` client. §4 extracts this into a public **`SafeOutboundTargetResolver`** + immutable `ResolvedOutboundTarget` with two explicit profiles: backwards-compatible safe fetch and strict webhook. Commerce validates at registration without a request; delivery resolves and pins exactly once through `safeWebhookRequestAsync()`. ONE resolver owns both policies without weakening webhook rules or breaking existing safe-fetch callers.
- The framework **queue** (`QueueManager::push`, `Job`) for async delivery + a scheduled recovery sweep.
- **NOT reused:** the global `WebhookDispatcher`/`WebhookSubscription`/`WebhookDelivery`/`DeliverWebhookJob` — they are un-scoped (no tenant/seller) and their persistence/retry semantics are tied to the global subsystem. Commerce owns its own scoped model.
- Commerce state-changing services publish seller-webhook snapshots through a transactional `SellerWebhookOutboxPublisher`; existing after-commit `BaseEvent` dispatch remains available to non-critical listeners but is NOT the webhook durability authority. MV5b lifecycle + the MV5c-1 `SellerApiKeyCapabilityCatalog` add the new management capability to its exclusions.

**Default-off:** marketplace master-off retains the existing zero-query fast path. With marketplace active but no matching seller endpoint, the outbox publisher performs at most one bounded indexed subscription probe, writes nothing, queues nothing, and leaves existing business behavior byte-identical.

---

## 1. Goal

Let a seller receive its OWN marketplace events at a registered HTTPS endpoint, reliably and securely: durable at-least-once delivery with signed payloads, bounded retries + dead-letter + replay, strict SSRF protection, strict per-seller isolation (a seller only ever receives events about its own resources), and MV5b-consistent suspend-pause / close-disable — reusing the framework's hardened signing + SSRF primitives while keeping all marketplace semantics in commerce.

---

## 2. Design

### 2.1 Ownership split
- **Framework owns:** HMAC signing (`WebhookSignature`), the SSRF-safe target resolution + IP-pinned no-redirect delivery client (via the new `SafeOutboundTargetResolver`, §4), and the queue.
- **Commerce owns:** seller-scoped endpoints, the durable event-snapshot + delivery outbox, retry/backoff/Retry-After, dead-letter, replay, consecutive-failure auto-disable, revision-based locking, per-seller event attribution + isolation, the suspend/close lifecycle, and the JWT-interactive seller management surface.

### 2.2 Endpoints (seller-scoped, revisioned, secret with rotation overlap)
- A seller registers one or more endpoints (`commerce_seller_webhook_endpoints`, §3): tenant, seller, HTTPS `url`, `subscribed_events` (JSON — exact event-type slugs, no wildcards; must be a subset of the published catalog §2.3), `status` (`active | disabled | deleted`), a mutation `revision`, `consecutive_failures`, `created_by`, timestamps. Per-seller, own-seller-only, tenant-bound.
- **Signing secret** lives in `commerce_seller_webhook_secrets`, encrypted with framework `EncryptionService` and AAD `tenant_uuid:endpoint_uuid:secret_uuid`. At any time an endpoint has exactly one `current` secret and at most one unexpired `previous` secret. Rotation retires any older previous secret, moves current → previous until `overlap_expires_at`, and inserts the successor as current in the same endpoint-revision transaction. The raw successor is returned ONCE; endpoint reads NEVER return any secret. The receiver already holds the predecessor and receives the successor during rotation; no dual-secret response header is required.
- Management mutations revalidate the actor's live seller membership + `webhooks.manage` capability **under the seller revision** (closing demotion/suspension races — MV5c-1/MV5b pattern).
- Manual/automatic disablement pauses the endpoint's remaining pending work with `pause_reason=endpoint_disabled`; no new snapshots target a disabled endpoint. `enable()` re-runs SSRF validation against the stored URL, resets the consecutive-failure counter, and resumes only that endpoint's `endpoint_disabled` deliveries. `DELETE` is a tombstone: set `status=deleted`, stamp `deleted_at`, revoke secrets, cancel pending/paused deliveries, retain endpoint/delivery/audit history, and refuse re-enable.

### 2.3 Event catalog, per-seller attribution + ISOLATION (the security heart)
- The v1 code-defined **event catalog** (`SellerWebhookEventCatalog`) is deliberately narrow: `order.placed`, `order.paid`, `order.canceled`, `seller_order.fulfilled`, `refund.completed`, `payout.recorded`, `stock.adjusted`, `product.adopted`, and `product.transferred`. An endpoint may only subscribe to catalog slugs. `refund.failed`, `order.note_added`, parent `order.fulfilled`, commission-policy, marketplace-lifecycle, discount, and late-payment events are deferred.
- `order.canceled` captures BOTH cancellation authorities: operator cancellation and stale-order expiry. `payout.recorded` means a payout row first becomes `paid`, covering manual insertion and the winning provider-success finalizer (never an idempotent replay). `stock.adjusted` means the explicit operator/seller `InventoryService::adjust()` operation only; checkout decrements and refund/cancel/expiry restocks are represented by their order/refund events and do not emit duplicate stock webhooks in v1.
- The transactional publisher **attributes each event to the participating seller(s)** and, per seller, builds a **sanitized per-seller payload** containing ONLY that seller's own resource data — its own seller-order + its own lines, its own payout, its own stock — NEVER another seller's data, the buyer's PII beyond what the seller legitimately owns, marketplace-internal fields, or any secret. Multi-seller order/refund events FAN OUT to one isolated snapshot per seller with a non-zero attributed share. `product.transferred` emits distinct transfer-out and transfer-in snapshots to the old and new seller; all other directly seller-scoped events attribute to their one seller. This isolation is the load-bearing security invariant (MV5c-1 leak-prevention discipline: allow-list projection, never a raw row spread).
- The event snapshot (`commerce_seller_webhook_events`, §3) stores the canonical payload BYTES (the exact bytes that get signed + sent), the event-type, seller, occurred-at, and a stable `event_id` (receiver dedup key).

### 2.4 Durable outbox, at-least-once delivery
- Seller-relevant state-changing services call an optional `SellerWebhookOutboxPublisher` **inside the same database transaction as the authoritative transition**. When matching endpoints exist, it writes the canonical event snapshot + one `commerce_seller_webhook_deliveries` row per endpoint before commit. An outbox write failure rolls back the business transition; there is no committed-state-without-outbox crash window. Existing `BaseEvent` dispatch may still occur after commit for mail/audit listeners, but webhook capture never depends on the fault-isolated event bus.
- Capture participates in the webhook lock order: claim participating seller revisions in sorted order (or reuse caller-held claims), re-read seller lifecycle state, then probe endpoint revisions. Active sellers produce `pending` deliveries; suspended sellers produce `paused` deliveries with `pause_reason=seller_suspended` and zero remaining delay. This serialization closes suspension-first versus capture-first: suspension-first can never leave a new deliverable row, while capture-first is included in the suspension transaction's pause set.
- Queue publication is registered with `afterCommit()` and is only a wake-up HINT. **The durable outbox is the authority;** a scheduled recovery sweep (`commerce:marketplace:webhooks:sweep`, host-cron) enqueues due pending rows and reclaims expired delivering leases. The plan must put capture at each v1 event's real transaction boundary: order placement attempt, paid transition, both cancel transitions, seller fulfillment, refund completion, manual/provider payout-paid points, direct inventory adjustment, and product adoption/transfer.
- **Delivery identity is stable across retries** (`delivery_uuid` + `event_id` in headers); receivers deduplicate. One failing endpoint never blocks another (independent per-delivery claim).

### 2.5 Signing (exact stored bytes)
- Each delivery signs the EXACT stored payload bytes (not a regenerated representation) with `WebhookSignature::generate($storedBytes, $currentSecret, $timestamp)` → the `t=…,v1=…` header. Headers also carry `delivery_uuid`, `event_id`, event-type, and a schema/version marker. New attempts use the CURRENT secret. An HTTP attempt that linearized before rotation may carry the previous signature; overlap keeps that signature verifiable because the receiver still holds the predecessor. No secret is ever in the body or headers.

### 2.6 SSRF-safe delivery (framework `SafeOutboundTargetResolver`, §4)
- **At registration / URL change:** commerce validates the URL via `SafeOutboundTargetResolver::resolveWebhook()` WITHOUT issuing a request. The framework resolver itself owns URL-host/IDNA canonicalization (there is no general framework `HostNormalizer`; commerce must not import tenancy's). It rejects credentials, fragments, non-default ports, IP-literal hosts, malformed IDNs, ambiguous host encodings, and non-HTTPS schemes; resolves ALL A/AAAA; and rejects the target if ANY address is in blocked space (private/loopback/link-local/metadata/reserved IPv4 or IPv6).
- **Immediately before EVERY delivery connection:** commerce calls the locked webhook client's `safeWebhookRequestAsync()`. That method invokes `resolveWebhook()` exactly once immediately before connection and applies the returned immutable `ResolvedOutboundTarget` (`canonicalUrl`, `host`, `port`, selected `ip`) to the client's resolve map. Commerce must not resolve and then pass the raw URL through a second resolving path: the address checked is the address pinned. This is the DNS-rebinding/TOCTOU boundary and preserves the original hostname for TLS SNI + certificate verification.
- NEVER follow redirects. Use short connect/read timeouts + strict response-size limits and the dedicated locked outbound client — no ambient cookies, proxy inheritance, local credentials, or internal auth headers.
- A safety-check failure is a **terminal delivery failure**, counts toward endpoint auto-disable (§2.7), and its seller-facing error NEVER exposes resolved internal addresses.

### 2.7 Retry / backoff / classification / dead-letter / auto-disable
- **Retryable:** network errors, timeouts, 408, 425, 429, 5xx. **Terminal:** any other 4xx (e.g. 400/401/403/404/410/422). Honor a **bounded** `Retry-After` for 429 and 503 (clamped to the max backoff). Retries use **bounded exponential backoff with jitter**; a configurable max-attempts limit.
- A terminal 4xx enters **`dead_letter`** immediately; a retryable delivery enters the same state only after exhausting its attempt budget. Both remain manually replayable (§2.8), with the terminal/exhausted classification retained in sanitized attempt metadata.
- **Crash-safe claim lease:** candidate discovery is unlocked. The worker transaction then claims seller revision → endpoint revision → delivery CAS, re-reads lifecycle/endpoint eligibility, sets `status=delivering`, a random `claim_token`, `claim_expires_at`, increments attempts, and commits before I/O. Finalization is conditional on the same token. The lease exceeds the configured HTTP timeout. The sweep discovers expired claims unlocked, then reclaims each through the same seller → endpoint → token/expiry CAS order, returning it to due `pending` (or current lifecycle-required paused/canceled state) and clearing claim fields. A late stale worker cannot finalize over the reclaimed attempt. A receiver may therefore see a duplicate after a lost response, which stable IDs make safe.
- **Auto-disable:** a per-endpoint **consecutive-failure threshold** flips the endpoint to `disabled`, durably audited, and pauses its other pending deliveries with `pause_reason=endpoint_disabled`. A success resets the counter only while the endpoint remains active. Explicit enable revalidates SSRF and resumes those deliveries (§2.2). Disable is per-endpoint — one failing endpoint never blocks or disables another endpoint.

### 2.8 Replay
- A JWT-interactive seller user holding `commerce.seller.webhooks.manage` may replay its own delivery. Replay creates a **NEW delivery attempt lineage referencing the original event snapshot**, WITHOUT mutating historical attempts (append-only history). Replay is available for `dead_letter` deliveries only while seller + endpoint are eligible; a `canceled` (closed-seller) delivery is NOT replayable (§2.9). An operator-wide replay surface is deferred.

### 2.9 Suspension / closure lifecycle (MV5b)
- Events generated while a seller is **`suspended`** are STILL written to the durable outbox; their deliveries enter **`paused`** with `pause_reason=seller_suspended` and consume NO attempts. Pausing snapshots `paused_at` and `paused_remaining_seconds = max(0, next_attempt_at - DB_NOW)` (new suspended events use zero). Reinstatement atomically restores only `seller_suspended` rows to `pending` with `next_attempt_at = DB_NOW + paused_remaining_seconds`, clears the pause fields/reason, and preserves attempt counts plus `(next_attempt_at, event.created_at, delivery.uuid)` ordering. Endpoint-disabled rows remain paused until explicit endpoint enable. The retry window therefore truly freezes instead of merely expiring while suspended. Endpoint MANAGEMENT is unavailable while suspended (like other mutating seller surfaces).
- **Closing** a seller disables all its endpoints and **terminally cancels** pending/paused deliveries (`canceled`) — retained for audit, NOT replayable. An in-flight HTTP delivery that STARTED before suspension/closure may finish and record its result; the lifecycle change does NOT attempt cancellation of an in-flight request.
- **Worker discipline:** candidate selection is not the claim. The claim transaction locks seller revision → endpoint revision → delivery CAS, re-checks eligibility immediately before that CAS, and commits. That successful claim is the in-flight linearization point: a lifecycle transition that wins first causes refusal/pause; one that commits after the claim treats the request as already in flight and may let it finish. The worker never claims delivery before seller/endpoint. The same lock order applies to management, lifecycle, auto-disable, and finalization.

### 2.10 Management surface (JWT-interactive-only)
- Seller self-service (new **`commerce.seller.webhooks.manage`** capability, granted to `seller_owner` + `seller_admin`; **excluded** from the MV5c-1 `SellerApiKeyCapabilityCatalog` so a seller API key can NEVER carry it), own-seller-only, tenant-bound, and gated **JWT-interactive-ONLY** (reuse `InteractiveSessionMiddleware`: `auth_provider==='jwt'` + no `api_key_uuid`, ordered before `commerce_seller:...webhooks.manage`). A machine API key can never register/redirect an endpoint or read/rotate a secret.
- Register endpoint (→ secret once), update (url/subscribed_events — url change re-runs SSRF validation; never returns the secret), rotate secret (→ new secret once + bounded overlap), disable, enable, tombstone-delete; list endpoints (no secret/deleted rows) + read retained delivery history (statuses/attempts/response codes, sanitized — no internal addresses); replay a dead-letter delivery. Every mutation durably audited (registration, URL change, secret rotation, disablement, enablement, deletion, auto-disable).

### 2.11 Coupling & continuity
- **framework → commerce** (framework `SafeOutboundTargetResolver` seam + `WebhookSignature`/queue reuse; commerce owns all data/lifecycle). No contracts/payvia. Default-off. Strict per-seller isolation. Consistent with MV5b lifecycle + MV5c-1 management-gate patterns.

## 3. Schema (commerce 1.2.0; new migration(s) `019+`, all `tenant_uuid` default `''`)
- **`commerce_seller_webhook_endpoints`**: id; uuid; tenant_uuid; seller_uuid; url; subscribed_events JSON; status (`active|disabled|deleted`) default active; revision int default 0; consecutive_failures int default 0; created_by; disabled_at/disabled_reason NULL; deleted_at NULL; created_at/updated_at. Uniques `(tenant,uuid)`; index `(tenant,seller_uuid,status)`. Secret held in a child table:
- **`commerce_seller_webhook_secrets`**: id; uuid; tenant_uuid; endpoint_uuid; `secret_ciphertext` text (framework encryption envelope; AAD `tenant:endpoint:secret`); optional non-secret fingerprint for support correlation; `relationship` (`current|previous`); `overlap_expires_at` NULL; created_at/revoked_at. No plaintext/hash-only signing source. Service/repository invariants enforce exactly one current + at most one unexpired previous under the endpoint revision; rotation revokes any older previous row.
- **`commerce_seller_webhook_events`** (durable snapshot): id; uuid (= `event_id`); tenant_uuid; seller_uuid; event_type; payload (canonical bytes); occurred_at; source ref(s); created_at. Unique `(tenant,uuid)`; index `(tenant,seller_uuid,created_at)`.
- **`commerce_seller_webhook_deliveries`**: id; uuid; tenant_uuid; endpoint_uuid; webhook_event_uuid; seller_uuid; status (`pending|paused|delivering|delivered|dead_letter|canceled`); attempts int default 0; next_attempt_at NULL; `paused_at` NULL; `paused_remaining_seconds` NULL; `pause_reason` NULL (`seller_suspended|endpoint_disabled`); `claim_token` NULL; `claim_expires_at` NULL; last_attempt_at NULL; last_status_code NULL; last_error NULL; replay_of_uuid NULL (lineage); created_at/updated_at. Index `(tenant,status,next_attempt_at)` (due sweep), `(tenant,status,claim_expires_at)` (expired-claim recovery), `(tenant,endpoint_uuid,status)`, `(tenant,webhook_event_uuid)`.
- Append-only **`commerce_seller_webhook_endpoint_events`** (audit): register/url_change/secret_rotate/disable/enable/auto_disable/delete + actor/reason. No secrets.
- `FixedSellerRoleAuthority`: add `WEBHOOKS_MANAGE = 'commerce.seller.webhooks.manage'` (owner+admin). MV5c-1 `SellerApiKeyCapabilityCatalog`: EXCLUDE `webhooks.manage` (keys never manage webhooks).
- config `marketplace.webhooks.*`: max_attempts, backoff base/cap, jitter, consecutive_failure_disable_threshold, secret_overlap_hours, delivery_timeout, `claim_lease_seconds` (> delivery timeout), max_response_bytes, retention days, sweep batch size.
- `DiagnosticsReport` + `CommerceTestCase::MIGRATIONS` + exact-list tenant-table pin + TenantAdopter gain ALL new tables.

## 4. Framework seam (REQUIRED — joins framework 1.71.0)
- **Extract `SafeOutboundTargetResolver`** (public) from `Client`'s private `assertSafeFetchUrl()`, plus immutable **`ResolvedOutboundTarget`**. It exposes two explicit profiles over one shared parse/canonicalize/resolve core: `resolveSafeFetch(url, allowPrivateHosts=false)` preserves today's `http|https` + operator-private behavior byte-for-byte; `resolveWebhook(url)` requires HTTPS and rejects credentials/fragments/non-default-ports/IP-literals/malformed-IDN/ambiguous encodings. Both resolve ALL A/AAAA; webhook rejects if any is blocked space; both return `{canonicalUrl, host, port, ip}` preserving hostname/SNI. There is no dependency on tenancy's `HostNormalizer`.
- Existing `Client::safeRequest()`/`safeRequestAsync()` call `resolveSafeFetch()` and retain their public behavior. New `Client::safeWebhookRequestAsync()` calls `resolveWebhook()` exactly once immediately before request creation and installs that returned IP directly in the resolve map; no check-then-second-resolution gap is allowed. Registration may call `resolveWebhook()` only for validation and discard that result — every delivery resolves afresh.
- This joins pending **framework 1.71.0** (with `dispatchOrFail` + `ApiKeyService::rotate`). `WebhookSignature` needs no change and is reused as-is. NO other framework change.

## 5. Surfaces
- Seller (`commerce_seller:commerce.seller.webhooks.manage`, own-seller, JWT-interactive-only): `POST /{sellerUuid}/webhooks` (register → secret once), `GET /{sellerUuid}/webhooks` (list, no secret/deleted tombstones), `PATCH /{sellerUuid}/webhooks/{uuid}` (url/events; url change re-validates SSRF), `POST /{sellerUuid}/webhooks/{uuid}/rotate-secret` (→ secret once + overlap), `POST /{sellerUuid}/webhooks/{uuid}/disable`, `POST /{sellerUuid}/webhooks/{uuid}/enable` (SSRF re-check + resume endpoint-disabled work), `DELETE /{sellerUuid}/webhooks/{uuid}` (tombstone), `GET /{sellerUuid}/webhooks/{uuid}/deliveries` (history, sanitized), `POST /{sellerUuid}/webhooks/{uuid}/deliveries/{deliveryUuid}/replay` (dead-letter only). Management and replay are refused while suspended.
- No operator/buyer surface change.

## 6. Off-invariance
- Marketplace master-off/non-marketplace paths retain the existing config-only zero-query fast path. In an active marketplace, no matching endpoint ⇒ one bounded indexed subscription probe at most, zero event/delivery writes, and zero queue work. Existing business results remain byte-identical; the new tables adopt/scope per tenant.

## 7. Testing (highlights)
- **Isolation (security heart):** a multi-seller `order.paid` fans out per seller; seller A's payload contains ONLY A's data (poison-string test proves no seller-B data / no buyer-PII-beyond-owned / no secrets / no internal fields leak); a seller only receives events for its own resources.
- SSRF: registration rejects http/credentials/IP-literals/private/loopback/link-local/metadata/malformed-IDN; delivery re-resolves + pins + rejects a DNS-rebind (public-at-registration→private-at-delivery); no redirects; internal addresses never in seller-facing errors.
- Signing: the exact stored bytes are signed; ciphertext is AAD-bound and decryptable through configured previous framework keys; plaintext is returned once only; new attempts use current while an already-linearized attempt may use previous during overlap; secret never leaks through reads, payloads, headers, logs, or audit.
- Reliability: retryable (network/408/425/429/5xx) vs terminal (other 4xx); bounded Retry-After honored; exponential backoff + jitter + max attempts → dead_letter; expired delivering lease is reclaimed and stale-token finalization refused; consecutive-failure auto-disable pauses sibling work; explicit enable SSRF-revalidates + resumes it; one failing endpoint doesn't block another; replay creates a new lineage without mutating history.
- Lifecycle: suspend → new deliveries `paused` with seller reason (no attempts consumed, remaining delay persisted); reinstate → DB-time restoration of seller-paused work only, preserving order/counts; endpoint-disable pause is independent; endpoint delete tombstones + revokes + cancels; close → endpoints disabled + pending/paused canceled (not replayable); claim commit is the in-flight linearization point.
- Durability: each v1 business transition and its matching snapshot/delivery rows commit or roll back together; an injected outbox failure rolls back the transition; enqueue-loss is recovered by the sweep; delivery identity is stable across retries (receiver dedup).
- **Live pgsql (mandatory, both orderings):** delivery-claim vs seller suspension (suspension-before-claim refuses/pauses; claim-commit-first is in flight); capture vs suspension (suspension-first writes paused; capture-first is caught by suspension); rotate-secret vs in-flight delivery (overlap keeps the in-flight signature verifiable); management mutation vs suspension; expired-claim reclaim vs stale-worker finalize (token CAS prevents stale overwrite). All use seller→endpoint→delivery lock order. Migration shape live.
- Off-invariance + tenant adoption for all new tables.

## 8. Resolved decisions
1. **Secret storage:** encrypted at rest with framework `EncryptionService`, endpoint-bound AAD, and returned once only. Hash-only storage cannot support signing and is rejected.
2. **Outbox boundary:** seller webhook snapshots + deliveries are transactional participants in the authoritative state change. After-commit events remain signals only; the recovery sweep repairs lost queue wake-ups, never a missing outbox write.
3. **V1 catalog:** exactly the nine slugs in §2.3. Internal/failure/note/parent-rollup/policy/lifecycle events are deferred until each has a seller-safe semantic and projection.
4. **Replay authority:** JWT-interactive seller self-service under `webhooks.manage`; no operator-wide replay surface in v1; canceled deliveries never replay.
5. **Framework seam:** `SafeOutboundTargetResolver` + `ResolvedOutboundTarget` expose backwards-compatible safe-fetch and strict-webhook profiles over one core. Existing safe requests preserve HTTP/private-host behavior; `safeWebhookRequestAsync()` enforces strict one-resolution IP pinning. Joins framework 1.71.0.
6. **Pause timing:** persist remaining retry delay and reconstruct it with DB time on reinstatement; retaining an absolute deadline alone is not considered frozen.
7. **Off-invariance:** true zero-query behavior is guaranteed only by marketplace master-off. An active marketplace with no matching endpoint permits one indexed subscription probe but no writes/queue work.
8. **Release:** framework 1.71.0 → commerce 1.2.0; seller webhook tables begin at migration 019 and first publish with Commerce 1.2.0.
9. **Delivery recovery:** `delivering` is leased, not terminally claimed; expired claims are recoverable and every finalizer is token-checked.
10. **Endpoint lifecycle:** disable pauses, enable SSRF-revalidates and resumes, delete tombstones/revokes/cancels, and auto-disable cannot leave endlessly re-enqueued pending rows.
11. **Event insertion points:** both cancellation paths are captured; payout means first transition to paid across manual/provider paths; stock.adjusted is direct `InventoryService::adjust()` only.
